14:T73b,An I/O completion can be stranded when a worker notifies the event loop between `eio_done_poll` stopping the async watcher and `eio_async_cb` restarting it. `ev_async_start` clears the pending notification, leaving a completed request queued without an event-loop callback.

Keep the watcher active while polling. Retain the required done-poll callback as a no-op because bundled libeio invokes it unconditionally.

2. Run `python3 check-eio-notifications.py /path/to/mettle baseline` against master (`4dd76ae`), then repeat with `candidate` against this branch. The probe extracts the actual callbacks and forces the worker to finish in the stop/start interval.
3. Confirm that both notifications are sent in each case, but only the corrected callbacks deliver both completions:

```text
mode=stop-start notifications=2 completed=1 pending=1
mode=keep-active notifications=2 completed=2 pending=0
```

15:T53a,An exited process can leave a dangling pointer in its channel. If the allocator reuses that address, closing the old channel can send `SIGINT` to a newer child. The [failing log](https://github.com/pauljccode/metasploit-framework/actions/runs/37078460668/job/111073508810) shows a new child receiving `SIGINT` immediately after delayed channel-close requests, consistent with this defect; allocator reuse was not captured.

Detach the process in the exit callback, allow cleanup after normal exit, and free the callback context on every exit path. Remove the read-time shutdown to avoid freeing the detached channel while `channel_read` still uses it. Non-interactive channels retain read-response-before-close ordering.

Related to [#64](https://github.com/rapid7/mettle/issues/64) and [#65](https://github.com/rapid7/mettle/pull/65), which addressed callbacks retaining a freed channel; this fixes a channel retaining a freed process.
